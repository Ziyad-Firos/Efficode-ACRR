# CodeT5+ fine-tuning — final result, documented

**Status: STOPPED, not abandoned.** Unlike the CodeBERT attempt
(`CODEBERT_DUPLICATE_DETECTION_PLAN.md`), this did not fail outright —
it produced a real, working, shipped feature. What stopped is further
attempts to raise the underlying model's accuracy through more training
runs. The infrastructure this effort built (differential verification
harness, hand-written training dataset, the fine-tuning notebook, the
live `/refactor` integration) all remain shipped and in use. This file
records the actual numbers and the decision to stop chasing a higher one,
so the reasoning isn't lost and this isn't re-attempted blind later.

---

## What was built (all shipped, independent of the model's own accuracy)

1. **A cross-platform differential verification harness**
   (`app/verify/sandbox.py`, `app/verify/differential.py`) — proves two
   versions of a function behave the same by running both on generated
   inputs and comparing outcomes, rather than trusting either version's
   code by inspection. Wired into the live Groq AI-suggestion path
   *before* any CodeT5+ work started, and it improved that path
   regardless of anything that happened afterward.
2. **A hand-written training-pair dataset** (`app/ml/t5/pairs.py`) — 10
   transformation families, every "before" and "after" side written
   directly as real Python (never generated by an LLM — see the file's
   own docstring for why that distillation trap was deliberately
   avoided), every pair validated against the harness above before being
   trusted. 250 pairs total; 2 families held out entirely to measure
   generalization, not memorization.
3. **A fine-tuning notebook** (`app/ml/t5/finetune_codet5p.ipynb`) — runs
   on a free Colab/Kaggle GPU, fine-tunes `Salesforce/codet5p-220m-py`,
   evaluates every generated held-out rewrite through the same
   verification harness, and reports the plan's go/no-go gate
   automatically.
4. **A live, opt-in `/refactor` integration**
   (`app/ml/t5/refactor_model.py`) — an off-by-default, clearly-labelled
   "CodeT5+ (local, slower)" toggle. Every generation is independently
   re-verified before being shown; a candidate that fails verification is
   returned with the disagreement shown, not silently dropped. This is
   still live in the app today, using the best weights actually produced
   (see below) — this document is not a removal notice.

## The actual numbers

Six real bugs were found and fixed across the notebook before a training
run ever produced a clean result: wrong git branch, wrong Python
interpreter, a stale tokenizer data format, a `Trainer` kwarg rename, T5's
documented FP16 instability, and NaN divergence in FP32 (fixed with a
lower learning rate, explicit warmup, and a fast-fail NaN guard). None of
those are open questions — each was root-caused and fixed, verified by
the next run's behaviour changing accordingly.

Once the pipeline itself was confirmed healthy (no more crashes, no more
divergence), **two real training runs** produced the only numbers that
actually test the model itself:

| Run | Dataset | Pass rate | Held-out families generalized | Gate 1 (≥95%) | Gate 2 (≥1 family) |
|---|---|---|---|---|---|
| A | 200 pairs, 8 families | **34%** | 2/2 (`minmax_in_loop_to_running` 2/25, `pop0_to_deque` 15/25) | FAIL | **PASS** |
| B | 250 pairs, 10 families (2 new families added specifically to teach run A's diagnosed weak spot) | **8%** | 1/2 (`minmax_in_loop_to_running` 0/25, `pop0_to_deque` 4/25) | FAIL | FAIL |

Per the plan, gate 1 failing on both is an unconditional no-go for
treating this as a trustworthy default feature. That was already known
after run A.

**The honest, uncomfortable part**: run B was expected to do *better*
than run A — it added training data specifically targeting the weak spot
run A's own per-family breakdown identified. It did worse, on both
metrics. The most likely explanation isn't that the added families hurt
on their own merits — it's that training on this small a dataset, this
briefly (both runs' best checkpoint landed within the first ~2-3 epochs,
a few dozen real optimizer steps, before validation loss started
degrading regardless of learning rate), is inherently noisy at this
scale. **Nothing in this setup was ever tested for run-to-run
reproducibility** — both A and B are single runs, not averages, so part
of the 34%→8% swing could be a real effect of task dilution (more
concepts to learn in the same short stable-training window) and part
could just be variance neither run controlled for. There is no way to
tell which from the data collected.

Three consecutive learning-rate reductions (5e-5 → 2e-5 → 5e-6) produced
non-monotonic results — catastrophic failure, catastrophic failure, 34%,
8% — rather than a converging trend. That pattern is itself the signal
that stopped further tuning: a fourth learning-rate guess wasn't
well-motivated anymore.

## What ships anyway, and why that's still honest

The live toggle uses **run A's weights** (34%, the better of the two) —
not run B's. Nothing about stopping here changes what's currently
running. The reasoning that made this safe to ship at 34% (documented in
`STUDENT_GUIDE.md` §15.6, local-only) holds exactly as well at any
accuracy number: every generation is re-verified before being shown, so
the pass rate controls how *often* the toggle produces something, never
whether wrong code can reach a user. That guarantee doesn't depend on
which of these two runs happened to produce the deployed weights.

## What it would take to actually raise the number (documented, not pursued)

1. **A reproducibility check** — rerun the exact same config (data,
   hyperparameters) 3-5 times and report a range, not a single number.
   Would answer the open question above directly. Not done here — costs
   real GPU time for a diagnostic rather than a fix.
2. **A different optimizer** — T5 fine-tuning literature generally
   recommends Adafactor over AdamW for exactly the instability pattern
   seen across every run here (destabilizing a few epochs in, regardless
   of AdamW learning rate). Considered and explicitly declined earlier in
   this project's history: Adafactor's well-calibrated learning rate is
   on a different scale than AdamW's (commonly ~1e-3 with
   `scale_parameter=False, relative_step=False`, not ~1e-5), and getting
   that wrong without the ability to test live risked trading one
   unverified guess for another. A real next step, not a quick one.
3. **More data, with a bigger effective training budget** — the actual
   constraint observed across every run was never "not enough diverse
   examples," it was "not enough *stable* optimizer steps before
   degradation." More instances per family only helps if paired with
   whatever actually extends that stable window (see #2, or a properly
   tuned warmup/schedule, or gradient accumulation revisited with the
   NaN-guard now in place to catch problems early rather than letting
   them run).
4. **A larger internal eval split** — 15-20 examples (10% of the trained
   set) is a small, noisy basis for `load_best_model_at_end` to pick a
   "best" checkpoint from, especially this early in training. A fixed,
   larger validation slice would make the reproducibility question in #1
   answerable with less GPU time per attempt.

None of these were pursued. This is a deliberate stopping point, not a
dead end nobody looked past.

## Bottom line

- **Gate 1 and the overall go/no-go: NO.** Not a trustworthy default
  feature by the plan's own bar, on either real run.
- **Gate 2: PASS on the better of two runs, FAIL on the other.** Genuine
  generalization was demonstrated at least once, not just memorization —
  but not reliably.
- **Ships anyway, deliberately, as an explicit experimental opt-in** —
  because the thing that actually protects users (differential
  verification) was true before either number existed and stays true
  regardless of which one is real.
- **The harness, dataset infrastructure, and integration code are the
  lasting result of this effort**, independent of the fine-tuned model's
  own ceiling — the same conclusion the plan itself predicted before any
  of this was attempted.
